# Сравнение поиска Cube555 на Kaggle и Molab

## Что именно сравнивать

У запуска есть два разных результата. Первый — путь, самостоятельно найденный лучом для заданной симметрии и направления. Второй — лучший проверенный путь для выдачи, который может происходить из другого запуска или исходного файла соревнования. Категория и источник сохраняются вместе с длиной.

Для №118 реальный отчёт Molab на версии `7bbe2e2` содержит 104 хода при луче 4 194 304, симметрии 0, прямом направлении и пределе 140 слоёв. Поиск прошёл 99 слоёв и достроил пять ходов из таблицы. Вычисление поиска заняло 10 902,621 с. В официальном sample есть 84 хода; группировка параллельных поворотов и сокращение их числа по модулю четыре дают 80 ходов. Полученная последовательность совпала со всеми 80 командами пользовательского CSV. Оба пути проверены воспроизведением на исходном состоянии. Для независимой оценки луча нужен журнал, в котором именно этот путь получен поиском с указанными параметрами. Повторный облачный результат для новой версии решателя ещё предстоит измерить.

## Алгоритм и код по этапам

| Этап | Kaggle TPU | Прежний Molab JAX | Изменённый Molab JAX |
| --- | --- | --- | --- |
| Система координат | При реверсе инвертирует перестановку, затем преобразует её выбранной симметрией из 48. После поиска переименовывает ходы в обратную сторону и при реверсе обращает последовательность. | Та же система. | Использует те же таблицы и повторно проверяет путь в исходных координатах. |
| Ширина | В указанной версии Kamilla `B_GLOBAL=4*1024*1024`. На восьми TPU-устройствах это 524 288 мест на каждое. | На №118 фактически задана та же глобальная ширина; на одном GPU представлены восемь логических секций. | Глобальная ширина, восемь секций и локальные квоты сохранены. |
| Оценка | Transformer `q555_f1_bell2k.pt` и ResMLP `q555_2k_BEST.pt` дают по 30 Q для ходов родителя. Веса 0,8 и 0,2. Меньшее значение лучше. Штраф за расхождение с V равен нулю. Индексы наклеек беззнаковые, 0–149. | Те же файлы по SHA-256, те же выражения JAX. Следует учитывать форму пакета и арифметику BF16. | Та же модель и веса. Одновременно рассчитывается пакет родителей одной секции. В отчёт пишется фактический размер пакета. |
| Организация слоя на большой ширине | Через 4 194 304 включительно секция оценивает весь свой луч, внутренний пакет Transformer по умолчанию 4096. | У №118 было 16 384 родителя в порции и 128 во внутреннем пакете; `vmap` допускал совместную обработку восьми секций моделью. | На этой ширине используются исходный полный слой секции и внутренний пакет до 4096. Память переиспользуется между отправителями. Для контрольного запуска на 8192 обе стороны могут явно установить 128. |
| Передача | 32-битный хеш перестановки выбирает владельца. При коэффициенте 2 каждый отправитель сохраняет до 131 072 кандидатов для каждого получателя. Оценка упакована в BF16 вместе с ходом и локальным индексом родителя. TPU выполняет `all_to_all`. | Обмен исходными восемью корзинами внутри виртуальной оси. | Буфер явно индексирован отправителем и получателем; перестановка этих осей даёт каждому получателю его восемь корзин в исходном порядке. |
| Отбор получателем | Стабильная сортировка по 64-битному хешу состояния, исключение повторов, пустых мест и совпадений с четырьмя предшествующими фронтами. После отбора нужно сохранить до 524 288 состояний. При нехватке допустимых кандидатов исходный код оставлял помеченные строки в следующем слое. | Унаследовал дефект. Такую строку можно было повторно расширить или поместить в историю. | Перед сохранением проверяется маска допустимости выбранного индекса. Отброшенные строки обнуляются, ходы получают маркер пустого слота. Только действительная строка может попасть в историю или дать встречу с целью. |
| Восстановление пути | Для каждого места слоя сохраняется `uint32` с рангом и индексом родителя и номером хода. Таблица радиуса 5 достраивает хвост. | То же дерево и таблица из 10 739 017 состояний. | Восстановленный результат повторно проигрывается в координатах поиска и в исходных координатах. Длины префикса и хвоста записываются раздельно. |
| Итог | Собирает минимум среди проверенных попыток по симметриям. При создании submission оставляет более короткий путь из базовой строки и найденного лучом. В скопированной версии за одно исполнение выбирается один случайный кадр. | Типичный запуск формы выбирал один фиксированный кадр и сообщал лишь собственную длину луча. | `solution` хранит собственный путь луча; `best_verified_paths` отдельно сравнивает его с проверенной официальной строкой. Для обоих кандидатов доступно точное сокращение параллельных поворотов. В таблице ноутбука видны обе длины и источник. |

У исходного **GPU-ноутбука** другая конфигурация. В сохранённом варианте два T4, запрошенная ширина 3 500 000 и фактическая ширина после выравнивания 3 506 176 (версия 485). Transformer/ResMLP смешаны 0,8/0,2. Параметры `SOLUTION_MODE="collect"`, `COLLECT_EXTRA_DEPTHS=1` и `MAX_COLLECTED_SOLUTIONS=2000` позволяют собрать несколько решений. Режим TPU выходит на первом слое встречи. Для сравнения длины важно записать и этот выбор. ## Что показала эмуляция

В локальном JAX 0.7.2 использованы действительные веса, 150 наклеек, все 30 ходов и исходная таблица финиша. №46 выбран по официально проверенному пути в 12 ходов. Для результатов ниже на обеих сторонах установлены ширина 256, S0, прямое направление, внутренний пакет 4 и предел 32. Код Kaggle работал на восьми XLA-устройствах CPU. Код Molab — на одном CPU с восемью логическими секциями. Тест сохранял и сравнивал **каждую строку каждого слоя**, начиная с исходного состояния, в том числе число копий, позицию, оценку и указатель на родителя.

* Исходный Kaggle и прежний Molab пришли к одному проверенному пути в 12 ходов (7+5), но первые различающиеся состояния были на слое 2. С каждой стороны по восемь лишних относительно другой стороны экземпляров. В исходном Kaggle среди 256 занятых мест оказалось 56 различных допустимых состояний и 200 помеченных строк. В исправленном Molab на этом слое сохранились ровно 56 допустимых состояний.
* При проверке исправленного правила на обеих сторонах состояние, порядок, оценки и указатели совпали на слоях 0–2. На третьем слое среди 256 допустимых состояний у каждой стороны оказалось по одному отсутствующему у другой. У семи общих пар «те же 150 наклеек родителя + тот же ход» разошлись Q. На слоях 4–7 мультимножества состояний снова совпали. В обеих реализациях итоговый путь имел ровно 12 ходов.
* У реального №118 сравнение 30 начальных оценок из Drive с исходной JAX-моделью на CPU дало 23 побитовых совпадения, максимальную разницу 0,25 и одинаковый лучший ход `-f0`. Это численное расхождение в вычислении модели при одинаковом входе. Его вклад в конечную длину 104 пока не измерен.
* На №118 дополнительно проверены первые шесть слоёв при ширине 256 с настоящими весами. Для обычного и порционного вычисления исправленного решателя на каждом переходе слоёв 2–6 совпали все 14 выходных массивов. Шесть коротких тестов размещения проверяют также точную цель, попадание в шар и исчерпание глубины.

Распределение мест и объём реально измеренного теста нужно указывать в выводе. Короткий тест на CPU проверяет логику перехода и восстановления. Максимальная скорость и расход памяти изменённого полного слоя при ширине 4 194 304 требуют измерений на GPU Molab.

## Как повторить без очереди Kaggle

1. Подготовить из датасета v3 оригинальные `jax_model.py`, `jax_beam_spmd_v_only.py`, две модели, раскладку и `bfs_endgame.npz`. Геометрия и порядок ходов задаются официальными `puzzle_info.json` и `test.csv`. Наш CLI проверяет контрольные суммы модулей исходного CPU-эталона, моделей, раскладки и таблицы. Зафиксировать ID, ширину, симметрию, реверс, внутренний пакет, число слоёв и версию кода.
2. Выполнить три запуска нижеприведённой команды в разных новых каталогах. Для физической эмуляции оригинала добавить `--original-cpu <каталог-артефактов>`, для исправленного алгоритма на восьми CPU добавить `--physical-cpu`, для размещения Molab на одном CPU оставить команду как есть. Во всех трёх использовать одни входные файлы и параметры.

   ```text
   python tools/tpu_solve.py --competition <каталог-с-test.csv> --assets <каталог-моделей> --output <новый-каталог> --pid 46 --beam 256 --depth 32 --device cpu --model-micro 4 --layer-audit
   ```

3. Сравнить все слои командой `python -m tools.tpu_reference.layer_audit <результат-A> <результат-B>`. Архивы `layer-NNNN.npz` содержат все строки состояний, оценки и указатели. Отчёт различает изменение мультимножества, перестановку слотов и изменение Q для идентичного родителя и хода. Первым исследовать самый ранний слой с расхождением соответствующего типа.
4. Проверить путь сборкой исходного состояния в цель. При сравнении симметрий вести отдельную строку на каждый кадр. Только после регистрации независимого результата луча сравнивать длину с минимумом из других кадров, официального примера и файла пользователя.
5. При повторе на реальном Molab сверить SHA из отчёта ядра с опубликованным коммитом, фактические `local_beam`, `model_micro` и `parent_chunk`, время полного слоя и обе длины результата. Для №118 критерий качества независимого поиска — новый самостоятельно найденный путь около 80 ходов; строка из сокращённого официального примера подтверждает только итоговую длину для выдачи.
